# PRD: backend (Nightlife Autopilot API)

Workstream: `backend` · Branch: `nightlife/backend` · Folder: `backend/`
Status: planning, revised for **Contracts v2.2** (Nov 11, 2026; contracts commit `acf7821`). No code yet.
Governing contract: [`docs/CONTRACTS.md`](../../CONTRACTS.md), including the v2 amendments
(§A–§J), which override the original text. Where this PRD and the contract disagree, the
contract wins. Section refs like "v2 §G" point at those amendments.

## 1. Problem

Nightlife Autopilot needs one service that every other piece talks to. Right now
there is a public-data SQLite DB (`data/manhattan_bars.db`), and plans for a
synthetic live-data simulator (`live-sim`, writing `data/live_sim.db`), a scoring package
(`ml-recs`) and a React app (`frontend`). Nothing connects them, nothing is deployed, and the
course's Nov 17 milestone is "working model, deployed". The Oct 13 "deployed team
skeleton" milestone was also never met, so the first backend task is a live
`/api/health` on a public URL.

The backend has to:
- serve venue profiles from the real public data, joined with synthetic live data
  that is clearly labelled and easy to swap for real data later;
- accept writes (scout vibe checks, owner updates, feedback) so the demo feels live;
- call `recs/` for live state, recommendations and routing, and keep working
  (with a simple stub) if `recs/` isn't ready;
- run locally with one command and on Render from `backend/render.yaml`.

## 2. Goals

1. Implement **every endpoint in the CONTRACTS.md HTTP API table plus the v2 §G additions**
   (`/api/auth/demo-login`, `/api/feedback`, heatmap `by=hour`), with the contract's JSON shapes.
2. One schema for the app's own (real) tables, defined in SQLAlchemy 2.0 with Alembic
   migrations, that runs on SQLite now and on Postgres by changing `DATABASE_URL`.
3. Read three sources: the app DB (real writes), `data/manhattan_bars.db` (public, read-only)
   and `data/live_sim.db` (synthetic, read-only, generated by live-sim), attached side by side
   (v2 §D). Real tables mirror their `syn_` twins; reads `UNION ALL`; `INCLUDE_SYNTHETIC=0`
   hides synthetic rows (v2 §E). That switch is the swap-to-real-data path.
4. Import `recs/` through a single adapter; fall back to a built-in stub with the
   same signatures, using the v2 §A constants, when `recs/` is missing or raises.
5. Simple auth: anyone can read; users, scouts and owners get a bearer token from demo-login to write.
6. `now=<ISO>` replay on every read endpoint; `DEMO_NOW=2026-11-14T23:30:00-05:00` (v2 §B).
7. pytest suite covering every endpoint, including the shared golden vectors G1 and G5; < 30 s.
8. Dockerfile + `backend/render.yaml`; deploy steps Ryan can follow once he has a Render account.

## 3. Non-goals (this phase)

- Real user accounts, passwords, OAuth, email verification, payments.
- Real-time push (websockets/SSE). The frontend polls (suggest every 60 s).
- Scoring logic beyond the stub. Scoring belongs to `ml-recs`; formulas to `specs` (v2 §A).
- Generating synthetic live data. live-sim generates every `syn_` table, including
  `syn_venue_events` (v2 §E). Backend keeps only a tiny test fixture generator.
- Reading evaluation-only tables (`syn_true_state`, `syn_scout_truth`) or `syn_scout_reputation_history`. The API never touches them.
- Editing `src/`, `data/manhattan_bars.db`, `data/live_sim.db`, or any folder another workstream owns.
- Dispute resolution UI/endpoints (specs defines the rules; `status` field exists, workflow later).
- Production hardening (rate limiting beyond a basic per-token cap, audit logs, backups).

## 5. User stories and acceptance criteria

IDs are `BE-n`. Each AC maps to at least one pytest test.

**BE-1 Health / skeleton.** As the team, I need a deployed URL that answers.
- AC: `GET /api/health` → `200 {"ok": true, "recs": "real"|"stub", "data": "synthetic"|"real"|"mixed", "demo_now": ISO|null}` (v2 §G), locally and on Render.
- AC: `data` is `real` when `INCLUDE_SYNTHETIC=0` or `live_sim.db` is absent, `mixed` when both real and synthetic rows exist, else `synthetic`.

**BE-2 Browse venues.** As a group, I want to list launch venues with their current vibe.
- AC: `GET /api/venues` with default `launch_only=true` returns exactly the 35 venues in `data/launch_venues.csv` (`license_id AS venue_id`).
- AC: each item is a venue card `{venue_id, name, display_name, style, genres[], price_level, typical_cover_usd, lat, lon, distance_km?, opening_hours, is_claimed, state, complaint_risk, is_synthetic}` (v2 §G). `state` is a Live Venue State.
- AC: `q` matches display name or address, case-insensitive substring. `style`, `genre` (shared vocabulary, v2 §E), `neighborhood` filter; unknown values → `[]`, not 400.
- AC: `limit` (default 50, max 200), `offset`; bare list + `X-Total-Count` header; `X-Data` header (`synthetic|real|mixed`).
- AC: venues without fresh reports have `state.vibe_score: null`, `state.display: "none"`; never a default number. Vibe labels (Chill/Lively/Packed) and the >60 min "stale" tag are frontend copy (v2 §J); the API only supplies `vibe_score` and `freshness_minutes`.
- AC: optional `lat`,`lon` query params fill `distance_km` and sort the list by distance (v2 §J); otherwise `distance_km` is null and order is by `display_name`.
- AC: attributes come from `data/venue_attributes_manual.csv` when present (`is_synthetic=0`), else `syn_venue_attributes` (v2 §D).
- AC: `launch_only=false` returns all 1,727 `v_bars` (most with null state and null attributes).
- AC: p95 < 300 ms locally for the 35-venue list (placeholder).

**BE-3 Venue detail.** `GET /api/venues/{venue_id}` → `{venue, state, recent_reports[], offers[]}` (v2 §G).
- AC: `recent_reports` = last 10 reports with status `accepted` or `pending` at `now`, newest first, with scout display name + reputation, never lat/lon.
- AC: `offers` = updates with non-null `offer` and `offer_expires_at > now`.
- AC: logs a `view` event to `venue_events`. Unknown id → 404 error envelope.

**BE-4 Live state.** `GET /api/venues/{id}/state` returns the Live Venue State (contract shape + optional `display`, `predicted_crowd`, `predicted_source`; v2 §F) computed at `now`.
- AC: report rows passed to recs include the scout's **current** `reputation` (from `scouts ∪ syn_scouts`; default 0.5) (v2 §F). The API never reads `syn_scout_reputation_history`; that table is for model training/evaluation (v2.1 §E).
- AC: inputs older than 180 min or with `ts > now + 2 min` are ignored (v2 §A) — recs does this; stub does too.
- AC: before any report that night: `n_reports = 0`, `vibe_score = null`, `freshness_minutes = null`, `display = "none"`.
- AC: stub reproduces golden vector **G1** (vibe 65 / conf 0.67).
- AC: logs a `tap` event.

**BE-5 Scout vibe check.** As a Scout, I submit crowd/dancing/line (+ optional cover, music) in ≤10 s.
- AC: `POST /api/reports` with a scout token and `{venue_id, crowd, dancing, line_minutes, cover_usd?, music_genre?, lat?, lon?}` → `201 {report_id, ts, status, points_pending}` (v2 §G).
- AC: server sets `report_id` (UUID4), `scout_id` (token), `ts` (now, America/New_York), `distance_m` (haversine to venue, int, null if no lat/lon), `verified_presence = 1` iff `distance_m ≤ 150` (v2 §A), `status = "pending"`. Raw lat/lon are never stored.
- AC: validation: crowd 1–5, dancing 0–2, line 0–180, cover 0–200, `music_genre` in the shared vocabulary → else 422.
- AC: owners cannot report their own venue → 403. Users (role `user`) cannot report → 403.
- AC: rate limit same scout + venue once per 15 min (placeholder) → 429.
- AC: points go to `points_ledger` (twin of `syn_points_ledger`): base + verified bonus + open bounty for that venue (bounty gets `claimed_by`, `claimed_at`). `points_pending` is the sum. Point values are placeholders until specs publishes them.
- AC: the next `GET /venues/{id}/state` reflects the report (pending reports count; flagged/removed don't).

**BE-6 Leaderboard and bounties.**
- AC: `GET /api/scouts/leaderboard?limit=20` → `[{rank, scout_id, display_name, level, points, points_week, reputation, is_synthetic}]` by points desc; `points_week` = ledger sum over the 7 days before `now`.
- AC: `GET /api/bounties` → open bounties (`claimed_by IS NULL` and `expires_at > now`) with all `syn_bounties` fields + `venue_name`.

**BE-7 Recommend.** `POST /api/recommend` with Preferences (+ optional v2 §F fields) → Recommendation results incl. `rank_score`, `rank`, `excluded_reason`, `cluster_label`, `complaint_risk`, `is_synthetic`.
- AC: sorted by `rank_score` desc (`match_score · (0.75 + 0.25·confidence)`); excluded venues last with `excluded: true` and an `excluded_reason`.
- AC: missing optional prefs allowed; invalid ranges → 422.
- AC: stub reproduces golden vector **G5** (match 83); unknown components score 0.4 and add a `missing` entry (v2 §A).
- AC: logs one `recommend_impression` event per returned non-excluded venue.

**BE-8 Run My Night.** `POST /api/plan-night` (Preferences + `n_stops` 1–5, default 3; `start_time`, `dwell_minutes`, `max_total_walk_minutes`, `exclude_venue_ids`) → stops `{order, venue_id, name, lat, lon, arrive_at, leave_at, walk_minutes_from_prev, distance_km, expected_vibe, match_score, confidence, reasons[]}` (v2 §F).
- AC: disabled (404 error envelope) when `FEATURE_ROUTING=0`.
- AC: stub = greedy nearest-next among the top 8 by `rank_score`, within `max_total_walk_minutes`.

**BE-9 Owner dashboard.** `GET /api/owner/{venue_id}/dashboard` with that venue's owner token → `{venue_id, views, taps, saves, reports_tonight, rec_appearances, demand_by_hour:[{hour, value}], is_synthetic}` (v2 §G).
- AC: counts from `venue_events ∪ syn_venue_events` and reports since 18:00 ET of the current night at `now`. Wrong/missing token → 401/403.

**BE-10 Owner update.** `POST /api/owner/{venue_id}/updates` with owner token, `{cover_usd?, dj?, genres?, event?, offer?, offer_expires_at?}` → `201` with the stored update; it shows in detail `offers` and the next state computation.

**BE-11 Heatmap.** `GET /api/heatmap?now=&by=hour` → `[{venue_id, lat, lon, hour?, vibe_score, confidence, n_reports, is_synthetic}]` for launch venues.
- AC: without `by`, one row per venue at `now`. With `by=hour`, one row per venue per hour 20–03 of the night containing `now`, state computed at **HH:30** of each hour (capped at `now`), matching live-sim's demo-night snapshots and Tableau's hourly cell (v2 §J).
- AC: disabled when `FEATURE_HEATMAP=0`. Null vibe stays null.

**BE-12 Replay.** Any read endpoint accepts `now`; default is `DEMO_NOW` env, else server clock.
- AC: rows with `ts > now` are ignored; offers/bounties active relative to `now`.

**BE-13 Demo login.** `POST /api/auth/demo-login {display_name, role: user|scout|owner, venue_id?}` → `{token, user_id|scout_id}` (v2 §G).
- AC: scout login creates a row in `scouts` (reputation 0.5, points 0); user login creates a row in `users`; owner login requires `venue_id` of a launch venue, one owner per venue (v2 §J): a second owner login for the same venue returns the existing owner's identity with a fresh token in demo mode (no 409, so the demo can't lock itself out).
- AC: disabled (404) when `DEMO_AUTH=0`.

**BE-14 Feedback.** `POST /api/feedback {user_id, venue_id, visited, rating?}` with a user token → `201`; stored in `feedback` (twin of `syn_feedback`, server sets `feedback_id`, `recommended_at` = latest impression for that user+venue or null) (v2 §G).

## 7. Requirements

### Functional
- F1. All contract endpoints, paths and field names exactly as in CONTRACTS.md + v2 §F/§G.
- F2. Read endpoints accept `now`; writes use server time (tests may override via `ALLOW_WRITE_NOW=1`).
- F3. Reads merge real tables with `syn_` twins (`scout_reports ∪ syn_scout_reports`, `venue_updates`, `venue_events`, `scouts`, `bounties`, `points_ledger`, `feedback`). `INCLUDE_SYNTHETIC=0` drops the synthetic side in one place.
- F4. Missing data is `null`, never a favourable default.
- F5. Every response object carries `is_synthetic`; list endpoints set `X-Data` (v2 §G).
- F6. `display_name` = OSM name when matched (all 35 launch venues have `osm_id`), else title-cased SLA name without LLC/INC/CORP; `name` = SLA name. Prefer `data/launch_venues_full.csv` (integration, v2 §D) and fall back to `manhattan_bars.db`.
- F7. `complaint_risk` = `{label: "311 noise-complaint risk", noise_complaints_3y, level}` from public data; never mixed into vibe or match (v2 §F).
- F8. Synthetic IDs start with `syn-`; real IDs are UUID4 (no collision).

### Non-functional
- N1. Python 3.12+ (container 3.12; dev box 3.13), FastAPI, SQLAlchemy 2.0, Alembic, Pydantic v2.
- N2. Render cold start < 60 s including generating/attaching `live_sim.db` (placeholder).
- N3. p95 < 300 ms for list/state endpoints; `/recommend` < 800 ms (placeholders).
- N4. CORS from `CORS_ORIGINS` (comma list); default `http://localhost:5173`.
- N5. No secrets in the repo. Tokens are random 32-byte strings stored as SHA-256 hashes.
- N6. JSON logs to stdout: method, path, status, ms, recs engine used.
- N7. `GET /openapi.json` is the machine-readable contract (v2 §G); Swagger UI at `/api/docs`.

## 8. Data sources

| Source | Kind | Access |
|---|---|---|
| `data/manhattan_bars.db` (`v_bars`, `osm_venues`) or `data/launch_venues_full.csv` | real public | read-only, attached as `pub` (SQLite) |
| `data/live_sim.db` (`LIVE_SIM_DB`) — all `syn_` tables | synthetic | read-only, attached as `sim`; generated by live-sim (seed 42), not committed |
| `data/venue_attributes_manual.csv` | real (hand-labelled), optional | loaded into app DB `venue_attributes` (`is_synthetic=0`) |
| App DB (`DATABASE_URL`) | real app writes | read-write: `users`, `scouts`, `api_tokens`, `scout_reports`, `venue_updates`, `venue_events`, `points_ledger`, `bounties`, `feedback`, `disputes`, `venue_attributes` — all created empty by migration `0001` (v2 §J) |

Every app table that has a `syn_` twin uses the twin's exact columns plus nothing required.
`data/live_sim.db` is generated at **build time** (Render build command / `make data`, live-sim target < 60 s for 36 nights; v2 §J), never at boot.
On Postgres there is no `ATTACH`; a build/release step copies `sim.*` tables into `syn_*` tables in the
same DB and the needed public rows into `pub_venues` (v2 §J).

## 11. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Render free tier sleeps / ephemeral disk | high | demo writes lost on restart | `live_sim.db` is baked into the image at build, so restarts only lose app-DB writes; warm 2 min before class; Starter + disk if Ryan prefers |
| `live_sim.db` build step fails or is slow | med | failed deploy | build fails loudly with live-sim's error; local fallback = fixture sim DB (tests/dev only, never silently in prod) |
| `recs` drifts from contract | med | 500s | Pydantic-validate outputs; per-call stub fallback |
| live-sim columns differ from v2 §E | med | wrong data | startup schema check prints exact column diff and falls back to fixture DB |
| SQLite ATTACH vs Postgres | med | Postgres path breaks | `repo/sources.py` hides table qualifiers; Postgres copy-in path (v2 §J); one Postgres test run |
| Timezone bugs in replay (night spans midnight) | high | wrong state | single `parse_now()`; UTC internally; tests at 23:59 / 00:10 / 03:00 |
| Demo tokens abused on public URL | low | junk reports | `DEMO_AUTH=0` switch, per-token rate limit, `ADMIN_TOKEN` reset endpoint |
| Very short timeline (Nov 13 18:00) | high | incomplete | deploy first, stub second, endpoints third; heatmap/plan-night behind feature flags |
